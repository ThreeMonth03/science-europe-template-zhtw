# 0.3.44：提交預覽接回共用來源

本輪整合三項已完成原型驗證的規則：系統漏填提示切換、計畫概要／品管短句整理、
未命名資料集的中性編號。不是從中文試作套件複製一份獨立 Jinja；正式來源仍在英文 repo，
中文透過 `pipeline.yml` 鎖定的既有轉換工具及翻譯樹產生。

## 這版的行為

- 內部檢核版仍是預設；漏填提示與原有文字保留。未知模式亦回到檢核版。
- 提交預覽只隱藏模板擁有的指定提示；使用者自行填寫的「尚待補充」、`N/A`、0、
  否定回答、檔名、網址及自由回答不能刪除，也不替使用者補寫承諾。
- 缺少概要欄位時不輸出該列；完全沒有內容的概要省略。真的填寫的補助編號與狀態保留。
- 固定品管方法與已勾選但未寫細節的「其他」合成一句，其他自由回答不併段或改標點。
- 名稱漏填時使用「儀器資料集 1」「參考資料集 2」等中性標籤，編號對應原問卷清單，
  不因篩選而重編，不把不同清單當成同一資料集。
- 六大節與十五題仍保留；不因沒有回答而整題消失，但不捏造答案填滿頁面。

## 翻譯整合找到的問題

轉換器原本將 `datasetLabel("instrument", ...)` 的分類參數抽成待翻譯字串。
若翻成中文，宏會失去分類。英文改用已命名的 `DATASET_*` 共用常數，只暴露顯示名稱。
來源檢查將這個明確改寫還原後，要求與已原生測試的英文原型逐檔雜湊一致。

原有 **748 組中英譯文全部保留**，沒有刪除或改寫既有譯文。新增 **14 組**：
五類標籤、兩種品管敘述（其中一種出現兩處）、限制與軟體的肯定事實，以及四個既有
補助狀態的新增出現位置。重新切分使翻譯文件路徑與機器註記變動；以來源／譯文配對的
計數、轉換結構審核和完整產出來源雜湊核對，不能只以路徑差異判斷是否漏譯。

實際新增譯文記在 `submission-preview-translation-delta.json`，不是在建置時呼叫 LLM。

## 檢查與證據界線

`probe_submission_preview.py` 直接載入本次建置的英文／中文來源，比較凍結原型及獨立
內容／編號檢查器。544 組涵蓋所有 65 組原有案例、三組額外案例、名稱全漏填變體及兩種
跳脫設定；亦檢查人員概要。預設／檢核／未知模式必須與 0.3.43 逐字相同。

`check_submission_preview_integration.py` 檢查實際套件、每個準備後來源檔、翻譯樹、
固定時間與衍生 UUID。CSS、字型、Lua、reference DOCX、格式 UUID／轉換步驟維持不變。

舊版檢核沒有停用：新來源驗證通過後，產生測試專用的精確 0.3.43 來源副本，再跑原本
0.3.43 → 0.3.42 → 更早版本的檢核鏈。歷史提示切換 oracle 仍測它原本負責的局部行為；
新版行為另由本輪檢查器覆蓋，兩者不能互相取代。`reviews/` 既有證據完全不改寫。

結構與套件通過本身不等於 PDF／Word 原生驗收。後續已用乾淨新版套件完成
[16 組原生整合對照](../reviews/2026-09-21-submission-preview-integration/README.md)：
四案例、中英、兩模式的全文、Word 組件及 PDF／LibreOffice 預覽逐頁座標與影像均重現
原型。這是另行產生的 0.3.44 證據，沒有將前輪 PDF／DOCX 改標成新版。
仍不是 Microsoft Word 原生目視或任意真實專案的全面驗收。

## 長期維護與下一步

兩個 repo 使用配對版號 **0.3.44**，中文鎖定英文完整 commit；仍在
`fix/profile-pagination`，沒有 merge main、release tag 或正式 DSW 上傳。
檢核版／提交預覽是同一版套件的不同輸出格式，不建立永久 review/submission 分支。
日後修改仍先英文來源 → 翻譯增量審核 → 配對建置 → 中英兩模式原生比較。

未完成：人名／計畫／資源／軟體名稱的佔位字、未命名資料格式、空的經費來源項目、
ORCID 解析，以及全域提示切換與完整視覺驗收。沒有宣稱任意專案已適合正式繳交、
符合全部 Science Europe／臺灣繳交要求，或通過 Microsoft Word 全面檢查。

目視後另外列入下一輪改善候選：未命名非參考資料集的短區塊仍可跨頁、第 9 題重複且
偏生硬的個人資料敘述，以及中性數字標籤與中文字的間距。這些與原型一致，並未因本輪
回歸通過就視為「閱讀品質已完成」。

## 第 9 題提示原型：內容通過，排版未通過

[第 9 題提示實驗](../reviews/2026-09-21-ethics-prompts/README.md)在名稱原型上，只改一個
Jinja 檔的兩處分支。536 組結構比對及八組中英原生內容比對通過，未刪除使用者填入
的相同句子；檢核版及已填控制維持原樣。這不是正式 0.3.45，也不是全面提交驗收。

**整合前阻擋：**中文漏填提交 PDF 的「處理個人資料的目的……如下」從第 3 頁移到
第 2 頁，第一段回答卻仍在第 3 頁。Word 預覽沒有這個問題。已增加可重跑的兩個唯一
文字錨點頁碼檢查，結果 `visual_gate_passed=false`，不能因內容與頁數檢查通過而放行。

下一輪先在來源端明確區分固定引導句與自由回答，讓引導句接到第一段回答；既有 PDF
`answer-lead` 與 Word 首段 keep-with-next 機制可作起點。不能整題／整段長回答 keep，
也不能在任意使用者原文中搜尋冒號或句號再切段。需涵蓋短／長／多段／清單／表格及
無回答控制，通過兩個引擎後再整合英文來源、翻譯增量及配對版號。

已確認的來源結構差異：第 9 題把 `sentences` 混合清單直接 join 到 `answer-detail`，
固定引導文字沒有 `<p>` 包裹。PDF 的 `answer-detail > p:first-child`／`answer-lead`
規則因此套不到這段裸文字；Word Lua 則會替 `answer-detail` 的第一個 Para 加上
`Pilot Lead` 樣式。下一個可驗證做法是在首次加入自由回答的來源位置記錄邊界
（告知說明、同意程序或處理目的），只將前方系統敘述包成引導段落，保留後方原文。
這仍是待驗證設計，不能把上述失敗原型直接當作修好的新版本。
